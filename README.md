<details open>
<summary><b>&nbsp;⟡&nbsp; Niyantran / AlphaQ — Intelligent Urban Traffic Optimization</b></summary>

<br/>

An end-to-end machine learning system that models Bengaluru's road network as a directed graph and optimizes signal timing and route selection using a stacked gradient-boosting ensemble, with an LLM-backed reasoning layer for human-readable operational recommendations. Advanced to **Round 2 of Flipkart Gridlock 2.0 among 4,500+ competing teams.**

| | |
| :--- | :--- |
| **Stack** | `Python` `CatBoost` `LightGBM` `MLflow` `FastAPI` `Groq LLM` `NetworkX` `Docker` |
| **Scale** | 294-junction Bengaluru road graph with weighted directed edges and live traffic feature ingestion |
| **Performance** | Stacked ensemble outperforming single-model baselines; sub-second inference on the full junction graph |
| **Security** | Rate-limited API surface, environment-isolated secrets, sanitized LLM prompt boundaries |
| **Impact** | Round 2 advancement in Flipkart Gridlock 2.0 (top tier of 4,500+ teams); deployed and publicly accessible |
| **Repository** | [![Live](https://img.shields.io/badge/Live-alphaq.duckdns.org-7C3AED?style=flat-square)](https://alphaq.duckdns.org) |

The core engineering challenge was not model accuracy in isolation — it was making a graph-structured prediction problem tractable in real time. I engineered topological and temporal features directly off the road graph, trained a CatBoost/LightGBM stack with MLflow-tracked experiments for reproducibility, and layered a Groq-backed LLM to translate raw model output into operator-facing recommendations without introducing latency into the critical path. The result is a system that reasons about a city-scale network and returns actionable output fast enough to matter.

</details>

<details>
<summary><b>&nbsp;⟡&nbsp; Live Train Tracker — Production Transit Intelligence Platform</b></summary>

<br/>

A production-grade backend that ingests live Indian Railways telemetry, predicts arrival delays using a trained XGBoost model, and serves low-latency queries through a Redis-fronted FastAPI layer with Celery-managed background ingestion.

| | |
| :--- | :--- |
| **Stack** | `FastAPI` `PostgreSQL` `Redis` `Celery` `XGBoost` `Docker` `AWS EC2` `GitHub Actions` |
| **Scale** | Continuous ingestion across live train schedules; horizontally scalable Celery worker pool |
| **Performance** | Redis caching layer collapsing repeat lookups to sub-millisecond reads; async request handling throughout |
| **Security** | Environment-scoped API credentials, parameterized queries, container-isolated runtime |
| **Impact** | Rebuilt from a Streamlit prototype into a deployable service with full CI/CD and infrastructure automation |
| **Repository** | [![Repo](https://img.shields.io/badge/GitHub-live__train__tracker-4C1D95?style=flat-square&logo=github)](https://github.com/shantanu-1607/live_train_tracker) |

This project was an exercise in taking something that *worked* and making it something that *holds*. The original prototype was a single-file script; the rebuild separated ingestion from serving, moved scheduled polling into Celery workers, introduced Redis as a read-through cache to absorb query bursts, and wrapped the whole thing in Docker with a GitHub Actions pipeline deploying to EC2. The XGBoost delay model runs as a distinct inference concern, not tangled into request handling.

</details>

<details>
<summary><b>&nbsp;⟡&nbsp; Simple Social — Async Social Platform Backend</b></summary>

<br/>

A fully asynchronous social platform backend built on FastAPI and async SQLAlchemy, with JWT-based authentication, media handling via ImageKit, and a clean separation between transport, service, and persistence layers.

| | |
| :--- | :--- |
| **Stack** | `FastAPI` `Async SQLAlchemy` `PostgreSQL` `JWT` `Pydantic` `ImageKit` `Streamlit` |
| **Scale** | Fully async request path with connection-pooled database access under concurrent load |
| **Performance** | Non-blocking I/O end to end; no synchronous DB calls in the hot path |
| **Security** | JWT access token auth, password hashing, Pydantic-enforced schema validation at every boundary |
| **Impact** | Reference implementation of a clean async Python backend architecture |
| **Repository** | [![Repo](https://img.shields.io/badge/GitHub-simple__social-4C1D95?style=flat-square&logo=github)](https://github.com/shantanu-1607/simple_social) |

The design goal was strict layering. Routes know nothing about SQL. Services know nothing about HTTP. Every input crosses a Pydantic boundary before it touches business logic. Async SQLAlchemy sessions are scoped per-request and never leak across the event loop. It's deliberately unremarkable in feature set and deliberately rigorous in structure — which is the point.

</details>

<details>
<summary><b>&nbsp;⟡&nbsp; PDF PII Redactor — Automated Document Sanitization Engine</b></summary>

<br/>

A document-processing pipeline that detects and irreversibly redacts personally identifiable information from PDF and DOCX files using spaCy named-entity recognition augmented with deterministic regex resolvers.

| | |
| :--- | :--- |
| **Stack** | `Python` `PyMuPDF` `spaCy NER` `Regex` `python-docx` |
| **Scale** | Batch processing across multi-page documents with per-page entity resolution |
| **Performance** | Single-pass extraction and in-place redaction without full document re-rendering |
| **Security** | True content removal at the PDF object layer — not visual overlay, not reversible masking |
| **Impact** | Eliminates a manual, error-prone compliance step in document handling workflows |
| **Repository** | [![Repo](https://img.shields.io/badge/GitHub-pdf__pii__redactor-4C1D95?style=flat-square&logo=github)](https://github.com/shantanu-1607) |

The subtle failure mode in most redaction tools is that they draw a black box over text and leave the text underneath. This one operates on the PDF content stream directly via PyMuPDF, so redacted spans are genuinely gone from the file. spaCy handles fuzzy entities like names and organizations; regex handles structurally rigid ones like emails, phone numbers, and identifiers — combining probabilistic recall with deterministic precision.

</details>

<details>
<summary><b>&nbsp;⟡&nbsp; Interview Call Manager — Scheduling & Coordination System</b></summary>

<br/>

A backend service for orchestrating interview scheduling, candidate coordination, and automated notification dispatch, built around a job-queue architecture with reliable retry semantics.

| | |
| :--- | :--- |
| **Stack** | `Node.js` `MongoDB` `BullMQ` `Redis` `Express` `HMAC-SHA1` |
| **Scale** | Queue-backed job dispatch with concurrent worker consumption and configurable retry policy |
| **Performance** | Asynchronous, non-blocking dispatch — scheduling requests return immediately, work happens off-path |
| **Security** | HMAC-SHA1 request signing for webhook verification and payload integrity |
| **Impact** | Reduced manual scheduling coordination overhead to a single automated workflow |
| **Repository** | [![Repo](https://img.shields.io/badge/GitHub-interview__call__manager-4C1D95?style=flat-square&logo=github)](https://github.com/shantanu-1607) |

The design constraint was that a scheduling request must never fail silently and must never double-fire. BullMQ over Redis gives durable job state and at-least-once delivery; idempotency keys at the handler level convert that into effective exactly-once behavior. HMAC-SHA1 signing ensures that inbound webhooks are actually from who they claim to be.

</details>
